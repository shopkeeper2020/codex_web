# 官方优先实现准则

本文档说明新增或修改功能时如何判断是否接入官方能力，避免 `codex_web` 与官方 Codex Desktop、VS Code Codex 扩展产生架构和行为分叉。

## 核心原则

- 先查官方文档、官方源码和协议 schema，再决定实现方式。
- 能通过 Codex app-server、official IPC 或 raw RPC 获取的数据和能力，直接接入官方接口。
- 官方已有业务逻辑不得在 Web 后端或前端重写一份。
- 官方已有数据不得写死，不得复制一份自定义落到本地 SQLite。
- 本地 SQLite 只用于官方没有覆盖的自定义扩展功能。
- 真实测试优先使用官方接口返回的数据，不用 mock 数据替代真实链路。

## 实现流程

1. 明确功能归属：判断这是官方能力复刻，还是 Web 端自定义扩展。
2. 查询官方材料：优先阅读 OpenAI 官方 Codex app-server 文档、`codex-rs/app-server` 源码和 `app-server-protocol` schema。
3. 核对 Desktop 行为：需要 UI 或交互复刻时，以实际 Codex Desktop 截图、运行表现和官方协议事件为准。
4. 选择接入方式：官方接口存在时直接接入；只有官方没有对应能力时，才允许新增自定义逻辑。
5. 记录证据：涉及协议、数据来源或 Desktop 行为判断时，在相关文档、测试或代码注释中保留简短证据入口。

## 数据约束

- 会话、线程、消息、工具调用、运行状态、配置等官方已有数据，应从官方接口或官方协议事件获取。
- 不应为了前端显示方便，把官方数据复制进 SQLite 再读取。
- 不应为了补齐 UI 字段而写死示例值、默认文案或模拟状态。
- 自定义扩展数据可以进入 SQLite，但必须与官方数据边界清晰，不伪装成官方来源。

## 代码约束

- 基于官方接口健壮性和本机互联场景实现，避免大段防御性代码、重复兜底和多层兼容包装。
- 不为未证实的异常 shape 预设复杂 fallback；遇到协议差异时应先回到官方文档、源码和 schema 核对。
- 前端仍不得直接依赖官方 raw protocol shape，必须经过 backend/domain 转换。
- 转换层只做必要的领域映射，不隐藏协议问题，不制造与 Desktop 不一致的新语义。

## 测试与验收

- 用户提供实际 Codex Desktop 截图时，应通过官方接口获取真实数据并与截图对比。
- 端到端测试优先跑真实 app-server / official IPC 链路。
- mock 只用于隔离极小单元、不可达外部条件或错误路径，不用于替代官方数据链路验收。
- UI 验收以 Desktop 实际展现逻辑为准，避免 Web 端自行定义不同的排序、分组、状态和文案。
